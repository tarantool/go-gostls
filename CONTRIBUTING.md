# Contribution Guide

## First steps

The project requires Go 1.25 or later. It is pure-Go and builds with
`CGO_ENABLED=0`; its only dependencies are
[go-gostcrypto](https://github.com/tarantool/go-gostcrypto),
`filippo.io/bigmod` and `golang.org/x/crypto`, all resolved from the public
module proxy.

```sh
$ git clone https://github.com/tarantool/go-gostls
$ cd go-gostls
$ go build ./...
```

## Branch naming conventions

When creating feature branches, follow these naming patterns:

- `<user.name>/gh-<issue-id>-short-description` (for GitHub issues)
- `<user.name>/gh-no-short-description` (for work not tied to an issue)

For release branches, use:

- `<user.name>/release-v<version>`

Replace `<user.name>` with your Git username, `<issue-id>` with the issue
number, and `<short-description>` with a brief description using lowercase,
hyphen-separated words. Do not use any symbols except numbers, letters and
dashes.

## Running tests

```sh
# Run the unit and round-trip tests for the main package and each subpackage:
make test

# Run the tests with the race detector:
make testrace

# Run the tests for a specific package (e.g., internal/handshake):
go test ./internal/handshake/

# Run a single test:
go test -run TestClientHandshake ./internal/handshake/ -v

# Bypass the build cache:
go test -count=1 ./...
```

A bugfix must ship with a regression test based on a reproducer: the test must
fail without the fix. Tests follow the Arrange-Act-Assert pattern and must not
depend on run order or on fixed sleeps.

### Test naming conventions

```go
Test<FunctionName>_<Description>
Test<StructName>_<Method>_<Description>
```

Examples from the codebase: `TestConn_Read_AfterClose`,
`TestClientHandshake_EmptyServerName`.

### Code coverage

```sh
make coverage
```

The module holds unit-test coverage above 80%; a change that drops it below
that is not merged.

### Interop tests

`TestGOSTEngineInterop` handshakes the pure-Go client against a real
`openssl s_server` driven by the GOST reference engine. It is behind the
`gostengine` build tag and skips itself when the engine is absent, so the
default test run needs no OpenSSL:

```sh
go test -tags gostengine -run TestGOSTEngineInterop ./...
```

CI builds the engine explicitly, so the job fails rather than silently skips.

### Fuzzing

Robustness fuzzers guard the attacker-facing wire parsers
(`internal/handshake.FuzzParseMessage`, `FuzzParseExtensions`, and the record
layer). The committed seed corpus is replayed by `go test`. To run mutation
passes over every target:

```sh
make fuzz FUZZTIME=1m
```

## Linting and formatting

The project uses `golangci-lint` v2 with a strict `default: all` configuration
(individual linters disabled with a documented reason) and `goimports` for
formatting.

```sh
make lint       # run golangci-lint
make lint-fix   # apply autofixes
make fmt        # gofmt in place
make vet        # go vet
```

The set of allowed imports is pinned by the `depguard` linter in
`.golangci.yml`. This module must never link GPL code or carry it in the
module graph.

## Spell checking

```sh
make codespell
```

## The pre-push gate

```sh
make ci   # lint + vet + test
```

## Code review checklist

- Public API exposes only what callers need from outside; everything else stays
  unexported or under `internal/`.
- Every exported function, variable and constant carries at least a
  single-line comment.
- Code is DRY.
- New features have functional and, where relevant, performance tests.
- No changes in files unrelated to the issue.
- No obviously flaky tests and no fixed sleeps.
- Bugfix commits carry tests based on reproducers.
- A changelog entry is present in `CHANGELOG.md`.
- Public API is covered by executable `ExampleXxx` tests with reference output.
- Autogenerated documentation looks good (`go doc -http=:6060`).

## Commit message guidelines

Commit messages have a subject, a body and issue references.

- Subject: `prefix: short description` — a short prefix, colon, space, and a
  lowercase subject in the imperative mood that completes "If applied, this
  commit will …". Keep it within ~50 characters, no trailing period. Typical
  prefixes: `core`, `api`, `lib`, `ci`, `tests`, `doc`, plus per-package
  prefixes such as `handshake:`, `record:` or `suites:`.
- Body: separated from the subject by a blank line, wrapped at ~72 characters.
  Explain what and why, not how.
- Issue references go in the last lines of the body, not the subject. Use
  `Part of #NNN` on intermediate commits and `Closes #NNN` on the final commit
  of a pull request.
- Use your real name and a working email address. Each commit is atomic and
  logically complete.

## Pull request process

1. Fork the repository and create a feature branch.
2. Ensure your code passes `make ci`.
3. Update `CHANGELOG.md` with a brief, user-facing description of your changes.
4. Open a pull request with a clear description of the change and its purpose.
5. A pull request is merged after two approvals and a green CI run.
